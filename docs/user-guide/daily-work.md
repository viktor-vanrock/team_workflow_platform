# Инструкции для команды QA и заказчика

[К началу руководства](README.md) · [Администрирование](administration.md)

Один человек может совмещать несколько ролей, например заказчика и исполнителя QA. Их назначает администратор доступов через **Пользователи и доступы**. Роли другой предметной области назначаются отдельно. После изменения нажмите **Обновить права**. Если областей несколько, переключайте предметную область; отдельный рабочий проект выбирать не требуется. Несколько ролей не разрешают подтверждать собственное действие.

В этом документе названия в кавычках соответствуют текущему интерфейсу.
Шаги с пометкой **API** выполняются через авторизованный API-клиент;
формы для них в обычном интерфейсе пока нет.

## Заказчик

**Роль:** описывает, что требуется проверить, предоставляет исходные данные
и получает результат. Локальная персона — `requester.alpha`, **«Заказчик»**.
Она может создавать и подтверждать запросы, уточнять входные данные в допустимом
состоянии и читать разрешённую очередь. Выполнение проверок и подпись заключения
требуют других прав.

### Подать запрос

1. Войдите как заказчик. Если проекта ещё нет, [создайте его с Hermes](customer-projects.md) или запросите проектное назначение у администратора.
2. Откройте **«Новый запрос»**, выберите нужный доступный проект. Укажите понятное название и выберите вид проверки.
3. Опишите цель, область и ожидаемый результат. Например: «Проверить вход после
   смены пароля»; ожидается, что новый пароль работает, а старый отклоняется.
   Укажите известные сведения о версии продукта, среде, ограничениях и сроках
   в подходящих полях формы. Неизвестные сведения предстоит уточнить с QA.
4. Нажмите **«Проверить запрос»**. Это сохраняет черновик и открывает резюме.
5. Проверьте резюме. При необходимости нажмите **«Изменить»**, исправьте данные
   и повторно сохраните их через **«Проверить запрос»**.
6. Нажмите **«Отправить запрос»** один раз. Дождитесь **«Запрос создан»**,
   затем нажмите **«Открыть запрос»**.

**Результат:** появилась подтверждённая заявка, доступная в разделе **«Запросы»**.
Само сохранение черновика не означает, что команда приняла работу.

Если связь пропала или обработка затянулась, нажмите **«Проверить состояние»**.
Не создавайте новую заявку, пока не выяснен результат прежней отправки.
Не закрывайте страницу до этой проверки: списка восстановления всех черновиков
в текущем API нет.

### Следить за работой и получить результат

1. Откройте **«Запросы»** и выберите заявку по названию.
2. Прочитайте подсказку **«Что дальше»**, статус в Jira и готовность QA.
3. Если QA не хватает информации, передайте уточнения исполнителю.
   Для принятого запроса изменение входных данных выполняется через API
   в разрешённом состоянии; это отдельная ревизия, которая может потребовать
   повторной оценки готовности.
4. В **«Очереди»** смотрите этап и порядок работы. Порядок меняет руководитель QA.
5. В карточке откройте **«Замечания»** и **«Заключение»**, ознакомьтесь с итогом
   и остаточным риском. Нажмите **«Обновить сведения»**, если данные устарели.

Для заказчика вкладки **«Проверки»** и **«Материалы»** сейчас показывают сводку;
редактор выполнения доступен исполнителю. Если нужны подробные материалы,
обратитесь к QA за разрешённым отчётом. Возможность увидеть кнопку согласования
внутри формы не даёт заказчику права подписать решение.

Обращения из Mattermost проходят отдельный приём: **«Дополнительно → Обращения из чата»**.
Сообщение в чате ещё не является подтверждённой заявкой. Следуйте шагам выбора
разрешённого проекта и подтверждения обращения; технический порядок подключения
описан в [runbook Mattermost](../runbooks/mattermost-hermes-intake.md).

## Исполнитель QA

**Роль:** готовит и выполняет проверки, сохраняет наблюдения, классифицирует
замечания, формирует первое заключение и инициирует закрытие.
Локальные участники — `executor.alpha` (**«Исполнитель QA · QA 1»**) и `executor.qa2` (**«Исполнитель QA · QA 2»**). У них одинаковые права во всех проектах рабочей области; проект выбирается отдельно.

### Подготовить работу

1. Откройте подтверждённый запрос в **«Запросах»**. Проверьте цель, область,
   сведения из Jira и актуальность исходных данных.
2. Во вкладке **«Готовность»** посмотрите оценку и наличие обязательного плана.
3. **API:** создайте оценку готовности. Если есть препятствия, уточните данные
   у заказчика или ресурсы у администратора. Допустимое исключение рассматривает
   руководитель QA; оно требует отдельного обоснования.
4. **API:** подтвердите готовность и дождитесь подтверждения внешнего состояния.
   Опубликуйте обязательный план сеансов по текущей оценке. Публикация доступна
   исполнителю и руководителю QA; [маршруты подготовки](#операции-через-api).
5. Убедитесь, что опубликованы нужные среда, QA-контекст и ресурсы, а проект
   разрешает выполнение. Если требуется тестовая учётная запись, получите lease
   через API. Это временное выделение аккаунта; по завершении освободите его.

Наличие нового запроса само по себе не создаёт план и не гарантирует доступность
среды. Если API отвечает `QA_REQUIRED_SESSION_PLAN_NOT_PUBLISHED`, сначала
выполните подготовку, затем вернитесь в браузер.

### Выполнить ручную проверку в локальном интерфейсе

Следующая последовательность показывает **успешный учебный сценарий**. Кнопки
этого экрана сохраняют заданные положительные результаты. Для фактического
отрицательного или неоднозначного результата используйте API с соответствующим
содержимым наблюдений, а не кнопку успешного завершения.

1. Откройте вкладку **«Проверки»** и нажмите **«Запланировать сеанс»**.
   Сеанс связывается с обязательным требованием опубликованного плана.
2. Нажмите **«Добавить проверку»**, пока сеанс запланирован.
   Текущая кнопка добавляет типовую «Ручную проверку» с заданным ожидаемым
   результатом; собственные пункты плана создаются через API.
3. Нажмите **«Подготовить»**, затем **«Запустить»**. Сервер проверит готовность,
   ресурсы и версии конфигурации. После старта цель и область фиксируются.
4. Перейдите в **«Материалы»**. Для пункта плана нажмите **«Начать попытку»**,
   выполните проверку, затем **«Завершить успешно»**.
5. Нажмите **«Зафиксировать положительное наблюдение»**, затем
   **«Зафиксировать успешный результат»**. Повторите для всех пунктов.
6. Нажмите **«Передать на проверку»**. В блоке **«Проверка подтверждающих материалов»**
   проверьте результат и нажмите **«Подписать проверку с результатом „Пройдено“»**.
   Для другого исхода review используйте API. Передача на проверку ещё не означает
   подписанный итог сеанса.

**Результат:** у выполненных пунктов есть попытки, наблюдения и результаты;
сеанс прошёл review, материалы и итог зафиксированы. В v1 для ручной проверки
не требуется загрузка бинарного вложения, и формы такой загрузки нет.

Если после старта нужно изменить зафиксированную цель или область, используйте
**«Создать связанную замену»**. Предыдущий сеанс остаётся в истории.

### Рассмотреть замечания и опубликовать дефект

1. Откройте **«Замечания»**, проверьте наблюдения и заполните
   **«Обоснование решения специалиста»**.
2. Для проблемы продукта используйте **«Классифицировать как продуктовый»**,
   затем **«Создать дефект»**. Это ещё не подтверждённый дефект в Jira.
3. При необходимости нажмите **«Предложить формулировку»**, проверьте текст
   и используйте **«Принять формулировку»** для создания черновика.
   Предложения помощника требуют человеческой проверки.
4. В блоке черновика нажмите **«Опубликовать»**. Если требуется согласование,
   передайте его другому уполномоченному руководителю QA.
5. Дождитесь появления записи в **«Подтверждённых связях с дефектами»**.
   Не считайте постановку команды в очередь подтверждением создания дефекта.

Принятие остаточного риска требует полномочий руководителя и отдельного решения.
Исполнитель не получает это право только потому, что классифицировал замечание.

### Запустить автоматические проверки

1. Откройте **«Дополнительно → Автоматические проверки»**. Текущий локальный экран
   автоматически использует первый запрос из доступного backlog; проверьте его ID.
   Для выбора другого запроса используйте API.
2. Проверьте режим **«Полный QA»** (`FULL_QA`) и текущую доступность автоматизации.
   `MANUAL_ONLY` позволяет только ручные сеансы.
3. Выберите опубликованный набор проверок (Suite), неизменяемую цель, тестовую
   среду, набор принятых параметров и браузер, если он предусмотрен набором.
4. Создайте автоматический сеанс и используйте доступные действия исполнения.
   Следите за состоянием попытки, pipeline и результатами проверки артефактов.
5. Рассмотрите полученные результаты и замечания. Повторный запуск оформляйте
   отдельной попыткой после выяснения исхода предыдущего.

Наличие GitLab в составе приложения ещё не означает готовую автоматизацию.
Если нет Suite, среды или опубликованных связей, передайте причину администратору.
Успешный pipeline сам по себе не подписывает заключение QA.
Список целей и наборов параметров в этом локальном экране демонстрационный;
он не является поиском произвольного MR или коммита корпоративного GitLab.

### Подписать заключение и запросить закрытие

1. Во вкладке **«Заключение»** выберите итог и классификацию остаточного риска.
   В поле **«Остаточный риск»** напишите, что осталось непроверенным или нерешённым.
2. Нажмите **«Создать черновик заключения»**, проверьте его и нажмите
   **«Подписать первым»**.
3. Для высокого или критического риска используйте **«Запросить подпись руководителя»**.
   Дождитесь независимой подписи QA Lead.
4. После полной подписи нажмите **«Оценить DoD»**. Если есть препятствия,
   устраните их и повторите оценку по актуальным данным.
5. При готовности к закрытию нажмите **«Подготовить закрытие»**, затем
   **«Запросить внешнее состояние „Выполнено“»**.
6. Передайте запрос согласования руководителю QA. После его решения нажмите
   **«Обновить точное состояние»** и дождитесь подтверждения закрытия из Jira.

**Результат:** сохранены подписанное заключение, оценка DoD и подтверждение
внешнего закрытия. Для пересмотра подписанного заключения укажите причину
и создайте замещающее заключение: старая подпись сохраняется в истории.

## Руководитель QA

**Роль:** управляет очередью и рисками, проверяет результаты, согласует операции,
требующие независимого решения. Локальная персона — `lead.alpha`,
**«Руководитель QA»**. У неё нет прав исполнителя на запуск ручного сеанса
и первую подпись заключения.

### Организовать работу

1. Откройте **«Очередь»**, проверьте этапы, актуальность и причины блокировки.
2. Для обзора нескольких разрешённых проектов используйте **«Все доступные проекты»**.
   Эта операция требует отдельного права `queue.portfolio.read`.
3. Для доступного к перемещению запроса используйте **«Переместить в начало»**
   или **«Переместить в конец»**.
   После операции обновите очередь. Изменение порядка не заменяет приоритет
   и статус Jira и не запускает проверку автоматически.
4. Если перемещение ожидает согласования, его должен рассмотреть другой QA Lead
   через API согласований очереди. В стандартном локальном каталоге один `lead.alpha`;
   повторный вход той же персоной не создаёт независимого согласующего.
5. Вместе с исполнителем проверьте DoR и обязательный план. Подтверждение готовности,
   публикация плана и запрос допустимого waiver выполняются через API.
   Исключение должно иметь причину и срок действия.

### Проверить и согласовать результат

1. Откройте запрос, ознакомьтесь с замечаниями, результатами и остаточным риском.
   Детальный review материалов доступен через API; сводка вкладки не заменяет его.
2. Рассмотрите запросы на принятие риска и исключения. Согласовывайте конкретную
   версию данных; при изменении оснований требуется новое решение.
3. Для ожидающего согласования дефекта используйте
   **«Согласовать как другой руководитель»**, если вы не инициировали публикацию.
4. Для частично подписанного заключения с запросом независимой подписи нажмите
   **«Подписать как руководитель QA»** после проверки высокого или критического риска.
5. Для подготовленного исполнителем закрытия нажмите
   **«Согласовать внешнее состояние „Выполнено“»**. Согласующий должен отличаться
   от инициатора закрытия.
6. Обновите точное состояние и проверьте подтверждение Jira. Ожидание worker
   или неизвестный внешний исход не заменяют это подтверждение.

**Результат:** очередь отражает согласованный порядок, исключения обоснованы,
закрытие и необходимые подписи имеют независимое человеческое решение.

При подключении проекта руководитель также выполняет функциональную приёмку
Binding и Suite по точным версиям ресурсов и успешному validation report.
Порядок описан в [инструкции администратора](administration.md#администратор).

## Читатель

**Роль:** просматривает разрешённые данные без изменения запросов и результатов.
В локальном стенде один читатель: `viewer.beta`, **«Читатель»**.

1. Войдите читателем. Выбирать отдельный рабочий проект не требуется.
2. Откройте **«Запросы»**, выберите заявку и ознакомьтесь со статусом,
   замечаниями и заключением в доступном объёме.
3. Откройте **«Очередь»**: она объединяет видимые задачи всех проектов рабочей области.
4. Если запрос не виден, уточните доступ у администратора рабочей области.
   Пустой список означает отсутствие видимых записей.

Локальному читателю доступна классификация до `RESTRICTED`. Право чтения
не разрешает изменять запросы, управлять очередью или экспортировать защищённые evidence.
Назначение роли действует в своей рабочей области; дополнительные области требуют
отдельного членства и прав.

## Операции через API

Для шагов, у которых ещё нет полной формы, используйте
[локальную OpenAPI-справку](http://localhost:5300/api/docs) и проверенную сессию
нужного участника. Swagger не получает вход из web автоматически.
Схемы запросов и обязательные заголовки смотрите для конкретной операции;
ETag берите из текущего ответа сервера, а версии и хеши — из возвращённых refs.

Ниже `Q` означает
`/api/v1/workspaces/:workspaceId/projects/:projectId/work-items/:workItemId/qa`.

| Задача                          | Маршрут                                | Кто выполняет                                                  |
| ------------------------------- | -------------------------------------- | -------------------------------------------------------------- |
| Оценить готовность              | `POST Q/readiness-assessments`         | Исполнитель; нужен текущий `If-Match` запроса                  |
| Прочитать оценки                | `GET Q/readiness-assessments`          | Участник с правом чтения запроса                               |
| Подтвердить готовность          | `POST Q/readiness-confirmations`       | Исполнитель или руководитель QA                                |
| Запросить исключение DoR        | `POST Q/waivers`                       | Руководитель QA; причина и срок                                |
| Получить заголовок плана и ETag | `GET Q/required-session-plans`         | Участник с правом чтения запроса                               |
| Опубликовать обязательный план  | `POST Q/required-session-plans`        | Исполнитель или руководитель; `If-Match`, причина и требования |
| Прочитать опубликованный план   | `GET Q/required-session-plans/current` | Участник с правом чтения запроса                               |

`GET Q/readiness-assessments` реализован сервером, но пока не описан в generated
OpenAPI. Для чтения истории оценок вызывайте его напрямую авторизованным API-клиентом.

Полные операции выполнения и review: [сеансы](../../apps/api/src/extensions/qa-sessions.controller.ts),
[ручное выполнение](../../apps/api/src/extensions/qa-manual-execution.controller.ts),
[review и манифест](../../apps/api/src/extensions/qa-session-review.controller.ts).
Контракты подготовки: [готовность](../../apps/api/src/extensions/qa-readiness.controller.ts)
и [план](../../apps/api/src/extensions/qa-required-session-plans.controller.ts).
Согласования очереди: [OpenAPI очереди](../../specs/006-queue-triage-capacity-sla/contracts/README.md).

Для работы с ресурсами и временными аккаунтами используйте
[onboarding API](../runbooks/onboarding-http.md). Защищённое чтение,
проверка подписи и экспорт описаны в [evidence API](../runbooks/evidence-http.md).

## Общая очередь и Hermes

Откройте «Очередь» или «Запросы»: в них собраны задачи всех проектов, к которым у вас есть доступ. На каждой задаче указаны проект и название. «Открыть задачу» ведёт в нужную карточку; хлебные крошки возвращают в общий список, а кнопки браузера «Назад» и «Вперёд» сохраняют путь.

При создании запроса укажите его проект. Этот выбор относится к новой задаче и не ограничивает общую очередь команды.

В «Предложениях помощника» выберите запрос, черновик или входящее обращение по названию и проекту. UUID вводить не требуется. Вы увидите сохранённые предложения Hermes или сообщение об их отсутствии. Это просмотр истории, а не запуск новой обработки.

У ролей администратора и читателя больше нет отдельных вариантов по функциям интеграций или наблюдения. Разные люди могут иметь одну роль; персональные ограничения классификации сохраняются. Для независимого согласования нужен другой человек.

### Как читать общую очередь

Вверху очереди находится компактная сводка: общее число задач, непустые этапы и актуальность данных. **«Обновить очередь»** обновляет задачи всех доступных проектов и их названия.

Все задачи показаны одинаковыми строками. Сначала идёт рассчитанный порядок, затем задачи с отметкой **«Без приоритета»**. Такая отметка означает отсутствие расчёта очереди, а не низкий приоритет или отсутствие доступа. **«Открыть задачу»** ведёт к запросу нужного проекта. Раздел **«Подробнее»** содержит состояние Jira, детали расчёта и, для QA-лида, разрешённые действия изменения порядка. Сводка располагается над списком даже тогда, когда у всех задач ещё нет рассчитанного приоритета.

## Создать свой проект с Hermes

1. Откройте «Создать проект с Hermes» и начните диалог. Пункт доступен заказчику даже без проектов. При корпоративном входе кнопка находится в карточке области на экране доступа.
2. Напишите название и цель, например: «Создай проект «Магазин» для проверки оплаты». Hermes уточнит недостающие сведения и покажет карточку.
3. Исправления отправляются сообщениями «Название: …», «Цель: …», «Ключ: …». Проверьте внутреннюю классификацию и стандартную критичность.
4. Подтвердите вход и нажмите «Создать проект». Он появится как черновик, доступный вам и рабочей команде. Подключения и готовность к работе настраиваются отдельно.
5. Диалог сохраняется на сервере. После сетевой ошибки повторите действие: один запрос не создаёт второй проект.

«Свои проекты» — назначенные вам проекты; внутри них видны все задачи.
Новые проекты других заказчиков в ваш список не добавляются. Локальный Hermes
ведёт сценарий сбора сведений; внешний LLM и нативная переписка с ботом Mattermost
пока не подключены.
