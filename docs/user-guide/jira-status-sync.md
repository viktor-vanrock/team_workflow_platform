# Как изменения статуса Jira попадают в платформу

Jira определяет рабочий статус запроса. Платформа хранит последнее подтверждённое
состояние Jira и отдельно — сеансы QA, результаты проверок и заключения. Например,
переход запроса в «Выполнено» не превращает заключение `FAIL` в `PASS`.

## После изменения в Jira

1. Jira отправляет webhook. API проверяет доставку и сохраняет задание в PostgreSQL.
2. Worker перечитывает саму задачу через Jira API: тело webhook служит сигналом для
   чтения. Статус, исполнитель, приоритет и срок берутся из ответа Jira.
3. Worker обновляет подтверждённое состояние и статус запроса в одной транзакции.
   Событие об изменении передаётся обработчику общей очереди для её пересчёта.
4. Вкладка **«Статус в Jira»** перечитывает данные платформы каждые 5 секунд.
   На ней видны исходный статус Jira, статус запроса и время последней проверки Jira.

Если webhook потерялся, worker автоматически ставит на проверку уже связанные задачи,
которые не перечитывались 60 секунд. Это порог постановки задания: при очереди или
недоступной Jira фактическая задержка будет больше. Перезапуск worker сохраняет задания.
Новые задачи такая фоновая проверка не импортирует.

Кнопка **«Обновить данные на экране»** перечитывает сохранённые данные платформы.
Она не выполняет непосредственный запрос в Jira. Ручную сверку всего проекта оператор
может запустить существующим API reconciliation с направлением `BOUND_REFRESH`.

## Если данные не совпадают

- **Актуально:** последнее чтение Jira подтверждено. Срок актуальности — 120 секунд;
  повторное чтение неизменившейся задачи продлевает его без новой редакции статуса.
- **Устарело / ошибка:** показано последнее подтверждённое состояние. При ошибке чтения
  задание остаётся в PostgreSQL; повтор выполняется через 5–60 секунд с учётом
  `Retry-After` Jira. Ошибка одной доставки не блокирует обработку остальных.
- **Неизвестный статус:** состояние не подставляется по имени или предположению.
  Появляется `MAPPING_REQUIRED`; нужно проверить соответствие статусов в интеграции.
- **Конфликт:** Jira изменилась после подготовки действия. Старое согласование не даёт
  права затереть новое состояние; требуется новое действие с актуальными данными.

Повторные и запоздавшие ответы не откатывают подтверждённый статус. При одинаковом
времени изменения учитывается порядок числовых идентификаторов истории Jira.

## Граница проверенного контура

Эта реализация и автоматические тесты относятся к локальным композициям `qa-jira-*`
с Jira API в Mock Hub. Планировщик выбирает только связанные запросы локального
подключения, совпадающего с адресом Mock Hub. Локальный workflow сейчас содержит
`Open` (ID `1`, статус платформы `NEW`) и `Done` (ID `2`, статус платформы `DONE`).
Новый workflow требует соответствующего mapping в коннекторе; неизвестный ID
отображается как ошибка настройки, а не как успешно синхронизированный статус.

Для корпоративной Jira отдельно проверяются подключение, утверждённое соответствие
статусов и доставка webhook. Прохождение локальных тестов не подтверждает настройку
внешнего сервера. Технические процедуры описаны в
[runbook Jira](../runbooks/jira-operational-authority.md).
