# ADR-0015: Первый корпоративный вход назначает администратора платформы

Дата: 2026-09-10. Статус: принято по явному запросу владельца продукта «кто первый вошел по корп учетке — тот имеет права полного админа». Заменяет требование доверенной группы и запрет выбора по первому входу из ADR-0013.

## Решение

Keycloak подтверждает личность через существующий проверенный OIDC code + PKCE callback. Все корпоративные пользователи допускаются по одному контракту issuer/audience/client без различий по группам. Первый проверенный HUMAN login новой платформы получает `access-administrator`: все существующие платформенные разрешения на каталог и управление членствами/ролями во всех Workspace. Рабочие роли, Project Entitlement, DENY, classification и независимое согласование сохраняются; администратор назначает рабочие роли себе и другим через редактор.

Регистрация identity, профиль, однократное назначение и запись о выборе выполняются одной транзакцией. PostgreSQL advisory lock сериализует входы всех API-реплик; singleton primary key допускает один результат на базу платформы независимо от issuer. «Первый» определяется успешным сохранением проверенного входа, а не открытием страницы или началом перенаправления. Ошибка БД откатывает всю транзакцию. При последующей ошибке доставки cookie выбранный человек сохраняет назначение и повторяет вход.

Неизменяемая запись `platform_administrator_bootstrap` хранит principal, источник и время. Отзыв роли, перезапуск и повторный вход не открывают выбор и не восстанавливают права. Срок токена, отзыв identity, CSRF и step-up для изменения доступов сохраняются. Непроверенные токены, неверный nonce/issuer, просроченные токены и SERVICE identity не получают назначение.

Последующие люди получают профиль без рабочих или платформенных прав. Рабочие действия проверяют текущие membership/roles/entitlements без ограничения `groups.mappings`; claims сами по себе ничего не назначают.

## Совместимость, миграция и rollout

Конституция 2.1.0 → 3.0.0: явное переопределение первоначальной корпоративной авторизации. Core 225 добавляет источник `CORPORATE_FIRST_LOGIN` и неизменяемую singleton-запись. На upgrade существующее корпоративное назначение, включая отозванное, закрывает bootstrap; оно не переписывается. Локальные демонстрационные назначения не занимают корпоративный bootstrap и не авторизуют корпоративную админку.

`createCorporateSessionBindings` включает новый режим по умолчанию (`accessProvisioning: true`). Старый объект `loginGroups`/`administratorGroup` отклоняется; host заменяет его на `true` и публикует новую ревизию session/group policy. `accessProvisioning: false` сохраняет специальный legacy режим заранее зарегистрированных identity с group mappings без автоматической регистрации/глобального назначения.

Rollout: migration 225 → обновлённая host policy и API → web → первый корпоративный вход → назначение рабочих ролей в `/admin/users`. На новой установке оператор первым завершает корпоративный вход перед передачей ссылки команде. Local seed и рабочие данные не сбрасываются.

Rollback: выключить provisioning, сохранить таблицу выбора, назначения и историю; исправления применять вперёд. Удаление записи выбора и автоматический down запрещены. Старый group-based host требует отдельного проверенного восстановления доступа, поскольку не знает новый источник назначения.

## Проверки

Реальный OIDC fixture и PostgreSQL: неверный nonce до первого входа, первый администратор без групп, второй ожидающий с теми же claims, выдача рабочих ролей без mapping, HTTP CSRF/step-up, запрет бизнес-доступа без назначения. Отдельные DB connections проверяют одновременные входы. Проверяются рестарт, повтор, отзыв, откат неудачного назначения, SERVICE/чужой issuer, upgrade с действующим и отозванным корпоративным администратором, независимость local bootstrap. Legacy group-scoped conformance сохраняется отдельным режимом.
