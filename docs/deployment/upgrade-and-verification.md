# Обновление стенда и эксплуатационные проверки

[Комплект деплоя](README.md) · [Локальный pilot](../runbooks/pilot-development.md)

Срез кода: 10 сентября 2026 года, включая bootstrap первоначальной области QA. Ниже приведён рабочий порядок для
локального Compose и требования к обновлению корпоративного host после завершения
[его сборки](pipeline-and-rollout.md). Локальные launchers работают только с LOCAL.

Для первоначального приложения QA порядок установки и обновления приведён
[в отдельной инструкции](initial-qa-workspace.md).

## Версии схем

Источник — [runtimePersistence](../../packages/runtime-composition/src/pilot/composition.ts).
Полный локальный pilot и корпоративные compositions `qa-jira-gitlab-mattermost-development`
и `qa-jira-gitlab-mattermost-test` выбирают следующий реестр:

| Namespace           | Версия |
| ------------------- | ------ |
| `core`              | 235    |
| `pack:dummy`        | 1000   |
| `pack:tech-writing` | 1100   |
| `pack:qa`           | 2110   |
| `connector:jira`    | 3050   |
| `connector:gitlab`  | 4020   |

`foundation` использует только Core, Dummy и Tech Writing. Наличие Tech Writing
в общем persistence registry не означает готовый корпоративный интерфейс писателя.
Не исключайте namespace из migration job вручную. DataSource не выполняет миграции
при обычном старте API/worker: `synchronize=false`, `migrationsRun=false`, транзакция `all`.

Проверить реестр без подключения к БД, из корня репозитория:

```sh
node --import tsx --input-type=module -e 'import { runtimePersistence } from "./packages/runtime-composition/src/pilot/composition.ts"; console.log(runtimePersistence("qa-jira-gitlab-mattermost-local").expectedVersions)'
```

Версии в работающем **локальном** pilot можно прочитать без изменения данных:

```sh
docker compose --project-name awp-local-pilot-dev --file infra/compose/docker-compose.local.yml exec -T postgres psql -X --set ON_ERROR_STOP=1 --username awp_runtime --dbname awp --command 'SELECT namespace, version FROM platform_schema_versions ORDER BY namespace;'
```

В корпоративном контуре выполните тот же SELECT через утверждённое соединение DBA.
Сравните все namespace с реестром выбранной composition; один номер Core недостаточен.

## Что меняют миграции доступа

| Core    | Изменение                                                                                                   | Проверка оператора                                                                                      |
| ------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 205–210 | Общая команда Workspace, объединение рабочих ролей                                                          | QA видит свои проекты; границы областей и DENY сохранены                                                |
| 215     | Каталог людей, назначения и история платформенного доступа                                                  | `/admin/users` открыт только уполномоченному пользователю                                               |
| 220     | Приватные диалоги проектов и проектные права заказчика                                                      | Заказчик видит назначенные проекты, чужие скрыты; недостающие назначения выдаются через редактор        |
| 225     | Первый проверенный корпоративный HUMAN login однократно назначает глобального администратора                | На новой установке первым входит назначенный оператор; существующий корпоративный bootstrap сохраняется |
| 235     | Квитанции первой области QA и её администратора                                                             | Только явный bootstrap пустой корпоративной установки; миграция сама не создаёт область/пользователей   |
| 230     | Старые локальные `LOCAL_BOOTSTRAP` назначения перенесены в историю; выбор первого локального администратора | После первого применения первым входит выбранный участник, до любых browser smoke/persona exchange      |

Миграция 220 сохраняет прежние общие requester assignments в snapshot. Она оставляет
проектные права на основании исторических Work Item/Intake Draft и текущих ответственных;
остальные проекты назначаются явно. Проекты, запросы и документы не удаляются.

Локальный выбор хранится в `local_administrator_bootstrap`, прежний seed — в
`local_administrator_seed_history`, корпоративный выбор — в
`platform_administrator_bootstrap`. Перезапуск, повторный seed и отзыв роли не открывают
выбор заново. Локальное назначение не авторизует корпоративную админку.
Точный контракт: [ADR-0015](../adr/0015-first-corporate-administrator.md),
[ADR-0016](../adr/0016-first-local-administrator.md).

## Обновить локальный pilot без потери данных

1. Зафиксируйте исходную и целевую ревизии. Перед обновлением используемого стенда
   сохраните backup PostgreSQL принятым у команды способом. Volume
   `awp-local-pilot-dev-postgres-data` содержит платформу `awp` и эмуляторы `awp_mock`.
   Само наличие volume не заменяет backup.
2. Переключитесь на Node 24.20.0 и pnpm 11.21.0. Для обслуживаемого стенда завершите
   текущие действия и остановите процессы, сохранив volume:

   ```sh
   pnpm dev:pilot:down
   pnpm install --frozen-lockfile
   pnpm prerequisites
   pnpm dev:pilot -- up --plan
   pnpm dev:pilot:up
   pnpm dev:pilot:status
   ```

   `up` пересобирает общий образ, применяет миграции и versioned seed. Исходники
   не смонтированы в контейнеры; для применения изменений требуется пересборка.
   `down` сохраняет данные. Не используйте `down -v`, удаление volume или reset
   как способ применения миграций.

3. Сначала проверьте сервисы без входа:

   ```sh
   curl --fail --silent --show-error http://localhost:5300/health/ready
   curl --fail --silent --show-error http://localhost:5310/health/ready
   curl --fail --silent --show-error http://localhost:54010/health/ready
   pnpm dev:pilot -- logs
   ```

4. На новой БД или после первого применения Core 230 первым войдите под выбранной
   учётной записью в [web](http://localhost:55173). Проверьте отметку **«Глобальный
   администратор»** и **«Пользователи и доступы»**. Затем разрешайте вход остальным.
   Не запускайте smoke, создающий сессию, до этого шага: автоматический HUMAN login
   также может занять единственный выбор.
5. Проверьте сохранённые проекты, запросы, документы и историю. Сверьте доступ
   заказчика к конкретным проектам, общую очередь QA и отдельную область писателей.
   Проверяйте создание/изменение сущностей на тестовом проекте с согласованными данными.

## Корпоративное обновление

Выполняется через реализованный host/release job по [pipeline runbook](pipeline-and-rollout.md):
общий backend digest, отдельная migration role, backup, fence и реестр выбранной composition.
Для старой схемы Core 185+ перед 190 используется
[read-only preflight](../runbooks/sql/0190-project-scope-preflight.sql).
Для чистой БД применяется весь registry; local seed на корпоративной БД не запускается.

При переходе на Core 225 замените прежний объект `accessProvisioning` в session factory
на `true` и обновите policy revision. `VITE_AWP_AUTH_MODE=corporate` задаётся при сборке web;
web и BFF используют общий HTTPS origin. Добавьте `/access` и `/admin/users` в разрешённые
return paths. После запуска проверьте первый вход, CSRF/step-up, назначение рабочих ролей
и отказ для второго пользователя без назначений. Подробности —
[корпоративный доступ](corporate-access.md).

Сохраняйте bootstrap-таблицы, назначения, историю, command receipts и invocation markers
при откате. Автоматического down migration нет; старый host может не понимать новые
источники прав. Возврат схемы требует проверенного recovery-плана, а неопределённые
внешние записи — readback исходной операции до возможного повтора.

## Диагностика после обновления

| Симптом                                            | Проверка и действие                                                                                                                  |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `PILOT_DEV_ENVIRONMENT_CONFLICT`                   | Уберите конфликтующие NON_PROD/runtime/composition настройки из shell и повторите `--plan`                                           |
| UI показывает старое поведение                     | Пересоберите через `dev:pilot:up`, обновите страницу и войдите снова                                                                 |
| Нет глобального администратора у ожидаемой персоны | Уточните, кто первым успешно вошёл; seed и рестарт не меняют выбор. Не удаляйте bootstrap запись                                     |
| Заказчик потерял часть каталога                    | Проверьте назначения конкретных проектов после Core 220 в `/admin/users`                                                             |
| API/worker не готовы                               | Посмотрите статус миграций и логи; в corporate проверьте совпадение policy, image/schema pins и регистрацию обоих процессов          |
| Jira-статус запаздывает                            | Проверьте worker, ошибки чтения и mapping; UI читает сохранённый статус. См. [синхронизацию Jira](../user-guide/jira-status-sync.md) |
| Результат внешней записи неизвестен                | Сохраните ID/ключ операции, проверьте ledger/readback; не создавайте новый effect key для обхода ошибки                              |

Полный локальный gate — `pnpm ci:008`; он запускает контейнеры и browser smoke,
меняет тестовые данные и управляет локальным pilot. Выполняйте его на выделенном runner
или тестовом стенде. PASS локальных проверок не является корпоративной приёмкой.
