# Корпоративный вход и первый администратор платформы

На dev bootstrap назначает супер- и платформенную роли существующим пользователям,
если указаны `AWP_SUPERADMIN_ENVIRONMENT=dev` и список subject в
`AWP_BOOTSTRAP_SUPERADMIN_SUBJECT` в dev values. Пользователь должен сначала войти;
повторный deploy не восстанавливает отозванные назначения. Рабочую роль снимают в
`/admin/users`; платформенная роль снимается отдельно с сохранением истории (редактор
рабочих ролей её не отзывает). При передаче проекта удалите обе настройки из
`envs/workspace-advosd-dev.yaml`. Первый корпоративный вход выбирается независимо от
DEV_BOOTSTRAP; если первым входит уже назначенный пользователь, существующая роль сохраняется.

Keycloak подтверждает личность. Роли и доступы назначаются внутри платформы; управление группами в Keycloak не требуется. Первый пользователь, успешно завершивший проверенный корпоративный вход на новой установке, автоматически получает `access-administrator` и открывает **«Пользователи и доступы»** (`/admin/users`). Все следующие пользователи появляются в каталоге со статусом ожидания.

Для [первой установки QA](initial-qa-workspace.md) уже есть Docker-образ и
корпоративный entry point. Его bootstrap добавляет область QA до первого входа;
первый администратор получает и `system-administrator` в этой области. Остальные
установки без QA bootstrap сохраняют прежний порядок: глобальная роль не создаёт workspace.

## Настройка собственного host и первый вход

1. Примените штатные миграции, включая core 225. Сохраните рабочую БД при обновлении.
2. В существующем host composition подключите `createCorporateSessionBindings` с проверенными `tokens`, `session`, шифрованием сессий, network и credential ports. Новый режим включён по умолчанию; можно явно указать:

   ```ts
   accessProvisioning: true,
   groups: {
     issuer: corporateIssuer,
     ref: corporatePolicyRef,
     mappings: [],
   },
   ```

   `groups` сохраняет issuer и ссылку на policy для совместимости контракта; mappings не определяют рабочие права в этом режиме. `corporatePolicyRef` должен совпадать с `session.policyRef`. При переходе со старого host замените объект `accessProvisioning: { loginGroups, administratorGroup }` на `true` и увеличьте ревизию policy. Старый объект отклоняется при запуске.

3. Добавьте `/access` и `/admin/users` в `session.returnPaths`. Соберите web с `VITE_AWP_AUTH_MODE=corporate`. Web и BFF должны использовать общий origin через reverse proxy.
4. После развёртывания первым войдите через корпоративную учётную запись, затем передайте ссылку команде. На `/access` появится кнопка **«Управлять пользователями и ролями»**. Источник роли в карточке — **«первый корпоративный вход»**.
5. После входа коллег назначайте им рабочие области, роли и классификацию в `/admin/users`. Для администрирования проектов назначьте себе `system-administrator` в нужных областях. Глобальная роль предоставляет все функции управления доступами; рабочие действия проверяют обычные права своей области и проекта.

Реальные issuer и client ID задаются оператором. Для host полного QA-пилота требуется [контракт composition](configuration.md); для первоначального приёма проектов используйте [готовый workspace host](initial-qa-workspace.md). `CorporateAccessModule.register(source, sessions)` подключается к `PilotNonLocalApiModule` при наличии `onboarding.sessions`; его также можно подключить отдельно для административного BFF. Полная рабочая QA-навигация требует корпоративного composition.

## Однократность и обновление

Выбор первого администратора происходит в PostgreSQL одной транзакцией с регистрацией identity, профиля и роли. Одновременный вход на разных API-репликах даёт ровно одного администратора. Перезапуск, повторный вход и отзыв роли не открывают выбор заново. Ошибка сохранения откатывает назначение; ошибка доставки cookie после сохранения устраняется повторным входом того же человека.

При обновлении установки, где уже было корпоративное назначение администратора, сохраняется существующее назначение. Даже отозванное историческое назначение закрывает автоматический bootstrap. Первый локальный администратор выбирается независимо и не занимает корпоративный bootstrap; локальные полномочия не дают доступ к корпоративной админке. Таблица `platform_administrator_bootstrap` хранит неизменяемую запись корпоративного выбора, а `platform_role_assignments` — действующее или отозванное назначение. Локальный порядок описан в [руководстве](../user-guide/administration.md).

Глобальную роль нельзя назначить через редактор рабочих ролей. Удалять запись bootstrap для передачи роли следующему пользователю нельзя: восстановление администратора требует отдельного серверного изменения назначения с сохранением истории. Откат версии сохраняет таблицы и назначения; разрушительного down нет.

## Контракт проверки личности

Сохраняются точные issuer/JWKS/audience/client ID, разрешённый алгоритм, discriminator access token, `client_id`, `jti`, времена токена, `nonce` в ID token и issuer в callback. `groupsClaim` можно оставить `groups`: отсутствие claim трактуется как пустой список. Названия групп или общая роль Keycloak не назначают права в платформе.

Секрет клиента и ключи cookie-сессий поступают через существующие credential/encryption ports; токены провайдера не передаются браузеру. CSRF, проверка Origin, отзыв identity и срок сессии сохраняются. Для изменения ролей по-прежнему требуется настроенный MFA/step-up: `acr`/`amr`, свежий `auth_time` и `session.stepUp.maximumAgeSeconds`.

Специальный legacy host может явно передать `accessProvisioning: false`: автоматическая регистрация и выбор администратора отключаются, используются заранее зарегистрированные identity и прежние group mappings. Для новой установки без управления группами оставьте provisioning включённым. Решение и миграция: [ADR-0015](../adr/0015-first-corporate-administrator.md).
