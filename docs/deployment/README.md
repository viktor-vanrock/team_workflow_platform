# Документы для корпоративного деплоя

Сверено с репозиторием 2026-09-10. Цель комплекта — первый корпоративный **NON_PROD**
стенд и последующий ограниченный пилот. Production/R4 в этот план не входит.

Для новой установки готов [запуск одной области QA](initial-qa-workspace.md):
миграции и bootstrap, корпоративный вход, первый администратор, управление участниками,
каталог, создание и редактирование проектов. API и web собираются в один Docker-образ.
Он рассчитан на приём карточек проектов без предварительных подключений к Jira/GitLab.

Для полного корпоративного QA-пилота открыта **008/T025** — API/domain worker,
provider effects и их приёмка. Инструкции полного пилота ниже относятся к этому
следующему этапу. Первая установка QA не закрывает эти обязательства.
Текущие schema pins и изменения Core 205–235 — в [инструкции обновления](upgrade-and-verification.md).

Паспорт — рабочая форма, не конфигурация, которую читает приложение. JSON-шаблоны
намеренно не проходят допуск, пока не заполнены. Они не создают публикации в БД,
не выдают доступы и не подтверждают корпоративные проверки.

## Порядок полного QA-пилота

1. Назначить delivery owner, заполнить паспорт и запросить данные у владельцев.
   Выбрать один Workspace/Project и корпоративный NON_PROD scope.
2. Параллельно завершить T025 и подготовить инфраструктуру. Получить актуальный
   локальный PASS для ревизии, из которой будут собраны release images.
3. Согласовать C1 и весь пакет metadata IN-01…IN-12. Для runtime нужны все 12
   записей, даже до первого фактического N2. Опубликовать политики и bindings.
4. Собрать и просканировать образы, сделать backup/preflight, выполнить миграции
   и первый запуск `integration` в согласованном тестовом scope.
5. На работающем стенде получить реальные N2, recovery и shadow доказательства.
   Только после них и точного human activation включить ограниченный пилот.
6. Собрать фактическое окно/выборку и human review. Сохранить решение и ссылки
   на доказательства в паспорте. Не считать запуск контейнеров приёмкой пилота.

Текущий пример `corporate:release` требует уже существующие N2 доказательства.
Он предназначен для последующего допуска и **не решает первый bootstrap**.
Отдельный bootstrap job и release wrapper входят в работу из
[инструкции по pipeline](pipeline-and-rollout.md).
