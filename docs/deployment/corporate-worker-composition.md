# Корпоративный worker: состояние сборки

**Состояние 2.2:** корпоративная точка входа и обработчики Jira, Mattermost,
GitLab reconciliation, очереди и onboarding собраны, но сквозная работа на
стенде не проверена. Проверка и публикация GitLab Suite закрыты: корпоративный
API возвращает `503` с сообщением «Недоступно: нет подтверждений runner, network
и no-deploy», а worker не начинает новые GitLab pipeline. Уже отправленные
команды остаются доступны для reconciliation. Коннектор 1.1.0 не включён.

Неполные части: GitLab events без настроенного publisher остаются в `READY`;
проверки provider capability дают `DEGRADED` и не подтверждают права записи;
каталог каналов ответа не подключён; Mattermost поддерживает только
`NONE_AMBIGUOUS`; внешний cleanup артефактов и скачивание через корпоративный
API не подключены. У contributions без собственной очереди или recovery есть
пустые служебные фазы: это не реализации отсутствующих возможностей.

Для запуска нужен образ с командой `pnpm --filter @awp/worker start:corporate`,
подготовленная БД (`AWP_WORKSPACE_DATABASE_URL` либо
`AWP_WORKSPACE_DATABASE_URL_FILE`, TLS/CA по настройке),
`AWP_ENVIRONMENT=NON_PROD` или соответствующий `AWP_RUNTIME_PROFILE`,
`AWP_COMPOSITION` для корпоративного Jira+GitLab+Mattermost,
`AWP_EXTERNAL_NETWORK_MODE=allowlisted`, `AWP_IDENTITY_ISSUER`,
`AWP_IDENTITY_AUDIENCE`, опубликованный `AWP_DEPLOYMENT_CONFIG`,
`AWP_CORPORATE_VAULT_CONFIG_PATH` и `AWP_RUNTIME_IMAGE_DIGEST`. При необходимости
задаются `AWP_CORPORATE_CA_PATH` и `WORKER_HEALTH_PORT`. Нужны Vault Kubernetes
auth, mappings read/write/webhook для провайдеров, актуальные опубликованные
политики и разрешённая сеть к БД, Vault, telemetry, Jira, GitLab и Mattermost.
Образ и манифест отдельного worker в этой работе не подготовлены. Точные
значения, роли и маршруты должны быть предоставлены владельцами стенда.

Подготовлена Jira-обработка `request.create` для `NON_PROD`: worker выбирает команды
только из проектов deployment, повторно проверяет сохранённый pilot admission и
конфигурацию, использует корпоративный Vault и сетевой transport. Контекст команды
изоляционно связан с текущим асинхронным вызовом; перед каждой записью фабрика
повторно загружает команду и проверяет её lease и права service principal.
Подтверждение создания требует фактического чтения Jira и использует полученного
reporter; локальная фиктивная идентичность в корпоративное подтверждение не записывается.
Для канала обратной связи корпоративное подтверждение явно сохраняет состояние
`MISSING`, пока нет проверенного корпоративного каталога каналов; локальные fixture
при этом не используются.
Подготовлены планировщик повторного чтения Jira и ограниченный deployment consumer.
Обработчик читает Jira через корпоративную фабрику, проверяет точные опубликованные
ревизии и discriminator проекта и нормализует статус по опубликованному Jira profile.
Поддержан только `VERIFIED_REPORTER`; другие режимы и import jobs отклоняются.
Сценарий ещё не проверен на стенде и зависит от актуальных настроек Jira profile.
Сохранённые привязки могут содержать ссылки `{id, version}` без `contentHash`;
worker сверяет хеш с опубликованной ревизией и дополнительно проверяет его в ссылке,
если он в ней присутствует.

`createCorporateWorkerContributions` собирает закрытый набор из десяти обработчиков.
GitLab reconciliation использует корпоративную фабрику
соответствующего проекта и фильтрует очередь чтения и курсоры по deployment.
Очередь и её временные переходы используют
фильтр проектов deployment до выбора очередной порции. Обработчики onboarding events, восстановления
проекций и retention ограничены проектами deployment; retention исполняет только
уже принятые решения, а внешнее удаление файлов не выполняет. Обработчик событий
GitLab ограничен deployment. Без publisher события остаются в состоянии `READY`,
обработчик только подсчитывает их и не подтверждает доставку. Для GitLab automation подготовлена фабрика с проверкой опубликованных
конфигураций и корпоративным transport, но сквозной путь ещё не подключён: запуск
автоматизации пока не подключён к корпоративному API. Подготовлен транзакционный writer
pilot admission и hook запуска автоматизации; до их подключения guard worker отклонит
команду. Снимать эту проверку нельзя: admission записывается в той же транзакции.
Подготовлен `startCorporateWorkerHost`: он загружает опубликованные политики,
Vault и telemetry, связывает guard с реально запущенным deployment и принимает
необязательный publisher. Точка запуска `apps/worker/src/corporate-main.ts` вызывается
командой `pnpm --filter @awp/worker start:corporate`;
манифест worker ещё не собран. Код нельзя считать сквозным сценарием
до их подключения и проверки.
Существующий локальный worker продолжает использовать свои фабрики.

Корпоративный worker подключает обработку результата GitLab к
`GitLabAutomationResultSyncConsumer`: повторно читает pipeline, сверяет commit,
маркер и опубликованные версии и использует отдельный доступ `ARTIFACT_SOURCE`.
Результат нормализуется по существующему контракту, а описания файлов собираются
из проверенного результата. При чтении pipeline, артефактов и исходного кода
повторно проверяются срок discovery и совпадение версии, сборки и редакции GitLab
с C1; при изменении или отсутствии подтверждения обработка откладывается.
Перед сохранением результата файл повторно читается и нормализуется; изменение
его содержимого или появление ранее отсутствовавшего файла откладывает сохранение.
Отсутствующий файл даёт `INCOMPLETE`, а отсутствие
артефактов обозначается как `UNAVAILABLE`. Для файла
результата берётся максимальная из разрешённых профилем классификаций, не ниже
классификации проекта; срок хранения сверяется с ответом GitLab. Если классификацию,
срок или другие факты нельзя подтвердить, обработка откладывается. Эти изменения
и сквозной сценарий ещё не проверены запуском тестов или на стенде.
GitLab может передать проверенный файл с исходом `INCOMPLETE`: QA сохраняет его с
`SCHEMA_VALIDATED` и без выдуманной ошибки нормализации. Отсутствующий или
некорректный файл остаётся `SYNTHETIC_INCOMPLETE`; ни один из этих исходов не
является успешным и не запускает автоматический повтор. Существующая JSON Schema
v1 допускает оба сочетания; код QA и новый CHECK миграции `2115` приведены к ней.
Миграция не меняет старые строки. Запись нового сочетания по умолчанию выключена:
сначала применяют миграцию и обновляют все потребители, затем задают worker
`AWP_GITLAB_VALIDATED_INCOMPLETE=true` и перезапускают его. До этого такие результаты
остаются в ожидании. Откат миграции запрещён, пока такие строки есть:
их нужно отдельно сохранить и обработать по согласованной процедуре.
Корпоративная выдача и скачивание зарегистрированных GitLab-артефактов через API
пока не подключены: имеющийся storage authority использует локальные данные и
заглушку секрета. Не использовать его в корпоративном host.
Корпоративный QA API предоставляет только защищённое чтение попыток, истории,
результата, решения о повторе и метаданных артефактов через существующие GET
маршруты с правом `qa.automation.read` и проверкой потолка для артефактов.
Создание сессии, получение подтверждения и запуск через этот модуль не включены.

Контракт результата требует `buildRef`, тогда как снимок цели COMMIT или
MERGE_REQUEST допускает его отсутствие. Для корпоративного запуска принят запрет
без непустого `buildRef`: проверка выполняется при транзакционном допуске команды
и повторно перед вызовом GitLab. Существующий HTTP-контракт передаёт `buildRef`
только для цели BUILD; для запуска через этот контракт нужно выбрать сборку.
Для передачи того же значения в CI существующий mapping профиля должен содержать
`logicalField: BUILD_REF`, `source: SUITE_PARAMETER`, `inputType: STRING` и
разрешённое имя входа GitLab. Схема параметров suite должна разрешать `BUILD_REF`;
его значение в параметрах должно точно совпадать с целью. Worker проверяет mapping
до запуска, поскольку иначе pipeline не получит идентификатор для файла результата.
CI должен включить это значение в `buildRef` файла результата по существующей
схеме `gitlab-pipeline-result@1.0.0`. Срок хранения result job должен быть виден
через GitLab `artifacts_expire_at` и удовлетворять ограничениям C1; если он не
подтверждён, обработка результата откладывается. Ограничения и классификации
артефактов сверяются с закреплённой политикой C1.
`artifactContract.artifactPolicyRef` и `artifactPolicyHash` в C1 должны совпадать
с закреплённой в попытке политикой; ссылка представляется как `<id>@<version>`.
Локальный pilot и схема не меняются. Корпоративный API запуска пока не подключён;
при его подключении нужно показать понятную ошибку пользователю и задействовать
`createCorporateTransactionalCommandAdmission`.

Worker проверяет политику повтора из C1, действующие права человека и сервиса,
карантин и актуальность исходной цели. Ссылки с номером проекта сверяются с C1;
неизвестный формат не используется для повтора. При записи нового запуска в
транзакции повторно проверяются права человека и карантин. После сбоя между
сохранением результата и решения о повторе предусмотрено восстановление. Всё это
ещё необходимо проверить запуском тестов и на стенде.
Просмотр результатов и восстановлений последовательно обходит все попытки внутри
deployment: неподтверждённые записи повторяются после обхода, но не задерживают
все последующие попытки в начале очереди. Курсор хранится в памяти worker и после
перезапуска начинает обход заново.
За один проход обрабатывается не более одного нового результата и одного
восстановления; так очередь результатов не занимает общий цикл на десятки
последовательных сетевых ожиданий.

Остаются незавершёнными корпоративное создание автоматизированных сессий и API
запуска, executor проверки Suite и доказательства write-capability probes. Локальные
адаптеры используют фиктивный проект GitLab и не подходят для корпоративного host.
Без опубликованных Suite, актуальных проверок и доверенного источника схемы её
параметров считать автоматизацию готовой нельзя.
Временный источник параметров — встроенный реестр схем образа: только закрытая
object-схема с ID `urn:awp:schemas:qa:automation-parameters:<имя>:v<номер>`.
Номер сверяется с `parameterSchemaRef.version`, хеш пересчитывается и сверяется
с публикацией Suite и реестром. Неизвестная схема, несоответствие хеша или лишние
поля блокируют допуск и обработку команды. Локальная заглушка `valid: true` к
корпоративному API не подключена. Для базового запуска добавлена схема
`urn:awp:schemas:qa:automation-parameters:build-ref:v1`: она требует `BUILD_REF`
и запрещает остальные параметры. При публикации Suite нужно закрепить версию 1
и точный digest этой схемы из сгенерированного реестра:
`sha256:c989e36d3d49642eb82af395f93edc6f67cfe32ebc02b4b9f63b553bf5d75e63`.
Значение `BUILD_REF` в
параметрах должно совпадать с выбранной сборкой. Владельцам CI нужно согласовать
значение и mapping; другие параметры требуют новой версии схемы. Техдолг: заменить встроенный реестр на корпоративный
источник опубликованных версионированных схем с проверкой происхождения и хеша,
сохранив fail-closed поведение и закрепление схемы в Suite.
Для будущего executor проверок Suite добавлен ограниченный выбор команд по
workspace, проектам и операции. Сам executor и его безопасное подключение ещё
отсутствуют; выбор scope не является подтверждением проверок Suite.
Для результата проверки необходимы реальные CI lint/dry-run и проверяемый пример
файла результата конкретного CI. Согласован путь `.awp/qa/result-example.json`
в закреплённом commit с проверкой по схеме результата; этот пример не доказывает,
что pipeline генерирует файл, поэтому отдельно нужен фактический артефакт из
прогона. Подготовлен GitLab connector v1.1.0 с отдельной операцией чтения
только этого файла по 40-символьному SHA commit; исходный v1.0.0 сохраняет
запрет и остаётся активным. Новый вариант не зарегистрирован в композиции и не
включён: перед включением нужны проверки и разрешающие только этот путь правила
сети и доступа. Для scoped egress binding путь содержит `.awp%2Fqa%2Fresult-example.json`,
а сетевая политика сопоставляет декодированный путь `.awp/qa/result-example.json`;
необходимо разрешить только `GET` и query `ref` для конкретного GitLab проекта.
Серверный адаптер для этого чтения подготовлен отдельно: он проверяет текущие C1,
grant, profile и connection, а также актуальный discovery версии 1.1.0 и берёт
SHA commit из него. До и после чтения он повторно проверяет полномочия и
неизменность конфигурации. Адаптер не подключён к executor или worker; результат
чтения помечен `provesPipelineArtifact: false`.
Отдельно подготовлена проверка фактического артефакта: сервер выбирает
единственный успешный pipeline для точных ref и commit и единственный успешный
job с закреплённым именем. При нескольких подходящих прогонах или неполной
странице выбор останавливается. Затем он повторно читает pipeline и job,
сопоставляет проект, commit, содержимое и схему и сверяет доступ до и после
обращения. Сейчас поддерживается только случай, когда `TEST_EXECUTION` и
`ARTIFACT_SOURCE` закрепляют один binding, profile и connection; иной случай
закрыт до реализации отдельного доступа. Результат пока не записывается как
evidence и не подключён к проверке Suite. Проверка не является QA-вердиктом.
Для выборки списков потребуются отдельно утверждённые маршруты GitLab `GET`
`/api/v4/projects/<project>/pipelines` с query `ref,per_page` и
`/api/v4/projects/<project>/pipelines/<pipeline>/jobs` с query `per_page`;
чтение артефакта использует `GET /api/v4/projects/<project>/jobs/<job>/artifacts`
с query `artifact_path`. Доступ проходит scoped egress и Vault; новые правила
сети в этой работе не включались.
Этот способ чтения соответствует текущему Mock Hub; для реального GitLab нужно
проверить и при необходимости адаптировать маршрут отдельного файла артефакта
(`GET .../jobs/<job>/artifacts/<artifact_path>`). До такой проверки нельзя
считать путь до корпоративного GitLab подтверждённым.
C1 v1 содержит только ссылку на схему результата, имя job
и путь артефакта. В таблице `gitlab_suite_contract_probes` хранятся только хеши, а
корпоративный создатель этих подтверждений отсутствует. Локальные fixture и
заполненные seed-ом хеши нельзя использовать как подтверждение корпоративного CI.
Нужно подключить и проверить сбор и сохранение фактических данных, прежде чем
executor будет выдавать успешную проверку. При этом чтение файла не доказывает,
что действующий trigger credential способен запускать pipeline. В C1 ссылки
`runnerReadinessEvidenceRef`, `containerReadinessEvidenceRef`,
`ciNoDeployAttestationRef` и `capabilitiesEvidenceRef` представляют собой только
строки: корпоративный источник и проверка содержимого этих подтверждений в коде
не определены. Без них нельзя надёжно установить `runnerReady`, `networkReady` и
`noDeployAttested`; заполнять их значением `true` по наличию ссылки нельзя.

События автоматизации сохраняются в базе, а очередь самостоятельно читает из
`event_outbox` события `qa.automation-attempt.status-observed` и
`qa.automation-attempt.completed` через собственный inbox, независимо от состояния
outbox. Остальные события Feature 005 этим потребителем не обрабатываются. Поэтому
подтверждать все события через publisher без получателя нельзя. Наличие этой очереди
само по себе ещё не завершает корпоративное подключение запуска автоматизации и UI.
Проектор разрешает ID попытки через `qa_automation_attempts` в ID QA-запроса в том же
workspace и проекте; независимые счётчики разных попыток не считаются устаревшими
относительно друг друга. Это исправление ещё не проверено запуском тестов.

Пакет C1 GitLab задаётся в опубликованном документе `CONNECTOR_BINDING` как поле
`gitlabPilotMetadata` соответствующего элемента `projects`. Это полный объект по
существующей схеме `gitlab-pilot-metadata@1.0.0`, без значений секретов. Публикация
с метаданными дополнительно проверяется при запуске: точные workspace/project,
contour, endpoint, hashes и ссылки binding/profile/connection должны совпадать.
Отсутствие поля сохраняет прежнее поведение запуска, но не даёт данных для обработки
результатов GitLab. Для автоматического повтора hash политики должен совпадать
с закреплённым за попыткой hash и с каноническим SHA-256 объекта `qaRetryPolicy`
без поля `policyHash`. Список ошибок и лимит берутся из этого проверенного объекта.
Ссылка политики должна совпадать с закреплённой в попытке строкой `<id>@<version>`.
Примеры с условными хешами для автоматического повтора не подходят.

Структура поля в опубликованном документе (остальные обязательные поля проекта
сохраняются):

```json
{
  "provider": "gitlab",
  "projects": [
    {
      "projectId": "<id проекта>",
      "integrationBindingRef": { "id": "<id>", "version": 1, "contentHash": "<sha256>" },
      "profileRef": { "id": "<id>", "version": 1, "contentHash": "<sha256>" },
      "connectionRef": { "id": "<id>", "version": 1, "contentHash": "<sha256>" },
      "gitlabPilotMetadata": "<полный объект C1, а не строка>"
    }
  ]
}
```

При изменении C1 нужна новая публикация и новая ссылка на неё в конфигурации
deployment. Пример — иллюстрация структуры, не готовый файл для публикации.

Техдолг: определить получателей остальных событий Feature 005 и способ их доставки,
реализовать publisher и проверить повторную доставку. До этого события остаются
в PostgreSQL в `READY`; запуск worker не означает, что они доставлены. Согласованное
временное решение — не терять и не подтверждать эти события без получателя.

Проверка допуска к probe использует точные ссылки опубликованного подключения и
текущие права сервисной учётной записи. Observer выполняет чтение проекта Jira,
проекта GitLab или учётной записи бота Mattermost через корпоративные фабрики.
Даже при успешном чтении он возвращает `DEGRADED` и
`PROVIDER_CAPABILITY_UNSUPPORTED`: это не подтверждает право на запись. Для полной
готовности нужны проверки возможностей записи и подтверждённые настройки провайдеров.

Подготовленная Mattermost-обработка обслуживает только `messaging.notify` в
канал проекта, заданный опубликованным профилем. Личные сообщения, callbacks и
intake пока не реализованы. Обработчик принимает только профиль и команду с режимом
`NONE_AMBIGUOUS`: неизвестный результат помечается AMBIGUOUS, повторный POST не
производится. Команды с `LOOKUP_REQUIRED` остаются ожидать реализацию поиска.
Подготовлен consumer подтверждения QA-запроса: intent, команда, admission и отметка
обработки сохраняются атомарно. Authority повторно проверяет право
`qa.request.confirm` у заказчика непосредственно перед отправкой; другие типы
уведомлений не разрешены. Для работы требуется опубликованный профиль с нужным
шаблоном, разрешённым каналом и `NONE_AMBIGUOUS`. Сквозная доставка пока не проверена.

Миграция `0255-notification-template-evidence` добавляет необязательное поле
`template_evidence`; существующие уведомления не меняются. Корпоративная отправка
требует свидетельство, точное совпадение с опубликованным профилем и валидацию
переменных по зарегистрированной схеме. Для `qa.intake.confirmed@1` хеш шаблона —
`sha256` от строки `AWP QA\n\nQA request confirmed: {{title}}` по стандартной
функции хеширования платформы. Откат миграции запрещён, пока в таблице есть
свидетельства: их необходимо отдельно сохранить и обработать.

Для новых QA Project Context можно использовать `qaValidationCapabilityRequirementSetV2.ref`:
в нём Mattermost использует `messaging.notify`. Проверки разрешают версию по точным
id, version и contentHash; прежняя версия 1 остаётся доступной. Существующий контекст
сам по себе не переключается: нужна публикация новой ревизии контекста и дальнейшее
штатное согласование. Пробел Jira `request.read` эта версия не исправляет.
