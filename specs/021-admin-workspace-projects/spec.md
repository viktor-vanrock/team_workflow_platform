# Feature Specification: Администратор проектов всех областей

**Feature Branch**: codex/workspace-wide-flow (existing authorized work)
**Created**: 2026-09-10
**Status**: Implemented and verified
**Input**: «Добавь администратору 1 доступ создавать проекты для всех воркспейсов, учти это в интерфейсе».

## User Scenarios & Testing

### User Story 1 — Администрирование проектов во всех областях (Priority: P1)
«Администратор · 1» создаёт проект в любой действующей рабочей области. Используется ограниченная роль «Регистратор проектов», назначенная отдельно каждой дополнительной области. Она разрешает создание проекта, просмотр каталога и настроек подключения; не выдаёт права управления интеграциями, доступами или предметными задачами. Назначения видны в управлении доступами.

**Why this priority**: Пользователь явно поручил расширить охват существующего администратора.
**Independent Test**: Один и тот же человек успешно регистрирует проекты в функциональной, изолированной и документной областях; второй администратор остаётся в прежней области.
**Acceptance Scenarios**:
1. **Given** текущий локальный стенд, **When** применяется обновление, **Then** у первого администратора есть право регистрации во всех действующих областях, а прежние роли и другие люди сохранены.
2. **Given** повторная развёртка или отменённое вручную назначение, **When** обновление повторяется, **Then** назначения и история не дублируются, отзыв не отменяется.
3. **Given** другой пользователь, **When** он пытается создать проект вне своих полномочий, **Then** получает отказ.

### User Story 2 — Выбор области в форме (Priority: P1)
На экране «Новый проект» администратор выбирает область по названию, видит её ответственных и создаёт проект именно там. Экран проектов доступен также при работе в области документации.

**Why this priority**: Новое право должно быть доступно через понятный рабочий экран.
**Independent Test**: Выбрать документную область из функциональной, создать проект, открыть его подключение и увидеть верную область; прежние ответственные не переносятся.
**Acceptance Scenarios**:
1. **Given** несколько разрешённых областей, **When** открывается форма, **Then** показан именованный список только областей с правом регистрации.
2. **Given** заполненная форма, **When** меняется область, **Then** название/ключ/причина сохраняются, ответственные выбираются заново из выбранной области, а старый ответ загрузки не подменяет новый.
3. **Given** работа в области документации, **When** администратор открывает проекты или создание, **Then** видит общий экран проектов; после сохранения ссылка открывает созданный проект правильной области.

### Edge Cases
Отозванное членство или роль; архивная область; область без существующих проектов; отсутствие подходящих областей; смена области во время загрузки; повтор одинакового тела в другой области; MFA без сброса выбора; потерянный ответ сохранения; новая область при следующей локальной развёртке.

## Requirements

### Functional Requirements
- FR-001: Расширить охват только первого локального администратора через ограниченную роль project-registrar в каждой действующей области без существующего права регистрации.
- FR-002: Сохранять прежние роли, классификацию и явные запреты; новые области получают обычный уровень допуска первого администратора.
- FR-003: Повторная развёртка не дублирует назначения и не восстанавливает отозванные права. Новые действующие локальные области подключаются при последующей развёртке.
- FR-004: Форма показывает только области, где текущая авторизация разрешает регистрацию; сервер повторно проверяет целевую область.
- FR-005: Выбор области загружает её людей, очищает прежних ответственных и отделяет повтор запроса от другой области.
- FR-006: Общие страницы проектов доступны в каждой предметной области независимо от её специализированного интерфейса.
- FR-007: После создания доступ и переход соответствуют целевой области; действующая очередь по-прежнему ограничена рабочей областью.
- FR-008: Подтвердить положительные и отрицательные сценарии автоматическими тестами, проверить UI и сохранить существующие рабочие данные при обновлении.

### Key Entities
Рабочая область; существующий администратор; назначение рабочей роли; целевая область нового проекта; запись применения локального обновления.

## Success Criteria

### Measurable Outcomes
- SC-001: Первый администратор создаёт проект в каждой из трёх текущих областей через один экран без ручного ввода идентификатора области.
- SC-002: Все проверенные попытки других ролей за пределами их областей отклоняются.
- SC-003: Повтор развёртки не добавляет новых назначений и не отменяет контрольный отзыв.
- SC-004: Смена области не переносит её ответственных, а созданный проект открывается в правильной области.

## Assumptions
Существующие административные права сохраняются только там, где они уже назначены. Регистратор получает три перечисленных разрешения; стартовый доступ к созданному проекту не расширяет их. Глобальная роль управления доступами остаётся отдельной; исключение из рабочей авторизации не вводится. Реальный Keycloak и создание новых областей остаются вне задачи. Нет новых человеческих учёток или сброса данных.
