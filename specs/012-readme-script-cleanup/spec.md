## User Scenarios & Testing

### User Story 1 — Первый локальный запуск (Priority: P1)

Разработчик открывает README, понимает назначение платформы, устанавливает зависимости,
запускает полный локальный контур, входит под тестовой персоной и находит диагностику.

**Why this priority**: Возможность воспроизвести проект — основа дальнейшей работы.

**Independent Test**: Пройти инструкции запуска и сопоставить команды, адреса и env с
репозиторием; проверить доступный локальный запуск без корпоративных учётных данных.

**Acceptance Scenarios**:

1. **Given** свежий checkout и необходимые инструменты, **When** разработчик следует README,
   **Then** он получает команды установки, запуска, статуса, логов и остановки.
2. **Given** необходимость изменить конфигурацию, **When** разработчик читает таблицы env,
   **Then** он понимает назначение, значения по умолчанию, способ передачи и область применения.
3. **Given** занятый порт или несовместимая версия инструмента, **When** запуск не проходит,
   **Then** README указывает диагностику и ограничения выбранного способа запуска.

### User Story 2 — Понимание и расширение платформы (Priority: P2)

Разработчик понимает путь запроса через платформу, границы компонентов и порядок
добавления Workspace, Project и пакета monorepo.

**Why this priority**: Документация позволяет продолжить разработку без угадывания.

**Independent Test**: Для каждого шага расширения найти точку в коде или явно указанное
ограничение текущей реализации.

**Acceptance Scenarios**:

1. **Given** новый участник проекта, **When** он читает раздел устройства,
   **Then** он различает Platform Core, Competency Pack, Connector, API, worker и web.
2. **Given** необходимость нового Workspace, **When** он следует руководству,
   **Then** он различает продуктовый Workspace и пакет monorepo и не ожидает несуществующего UI.

### User Story 3 — Понятный набор команд (Priority: P2)

Разработчик видит в корневом package.json поддерживаемые команды разработки и общие
проверки; вспомогательные команды этапов остаются доступны через существующие инструменты.

**Why this priority**: Исторические aliases скрывают ежедневные команды.

**Independent Test**: Сравнить набор команд до и после, проверить их потребителей в CI и
инструментах и доступность замены каждой удалённой команды.

**Acceptance Scenarios**:

1. **Given** избыточные команды этапов разработки, **When** выполняется очистка,
   **Then** список сокращается по явным критериям без удаления реализации проверок.
2. **Given** общие проверки проекта и локальный запуск, **When** очистка завершена,
   **Then** их зависимости разрешаются и текущие инструкции используют существующие команды.

### Edge Cases

- Корневой `.env` и контейнеры могут иметь разные механизмы загрузки переменных.
- Узкие локальные профили и полный pilot используют разные порты и начальные данные.
- Редко вызываемая человеком команда может быть обязательной зависимостью CI.
- Исторические документы могут ссылаться на удалённые aliases: нужен путь к эквивалентному запуску.
- Некоторые проверки требуют Docker или корпоративных данных; результаты нельзя выдумывать.

## Requirements

### Functional Requirements

- **FR-001**: README ДОЛЖЕН описывать назначение, текущие возможности и ограничения проекта на русском.
- **FR-002**: README ДОЛЖЕН содержать полный основной сценарий локального запуска и управления сервисами.
- **FR-003**: README ДОЛЖЕН объяснять все переменные корневого env-примера, настройки локального
  контура (допускается отдельный справочник по ссылке) и конфигурацию реального деплоя, включая загрузку и значения по умолчанию.
- **FR-004**: README ДОЛЖЕН описывать структуру репозитория и путь обработки запроса.
- **FR-005**: README ДОЛЖЕН разделять добавление продуктового Workspace, Project и пакета monorepo,
  указывать реальные точки расширения и отсутствующие возможности самообслуживания.
- **FR-006**: Из корневого списка ДОЛЖНЫ быть удалены избыточные aliases с сохранением основных
  команд запуска, качества и работающих агрегатных проверок.
- **FR-007**: Для удалённых aliases ДОЛЖНА быть доступна точная замена; активные вызывающие
  инструменты и документация ДОЛЖНЫ оставаться согласованными.
- **FR-008**: Изменения ДОЛЖНЫ пройти применимые проверки; ограничения среды фиксируются отдельно.
- **FR-009**: Feature ДОЛЖНА содержать spec, plan, research, quickstart и завершённый список tasks.
- **FR-010**: Настройки реального деплоя ДОЛЖНЫ быть отделены от local/test env: в README указан
  обязательный набор API/worker, необязательные значения, отдельные настройки сборки web и Collector;
  подробности локальных проверок вынесены в отдельный справочник.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Основной сценарий содержит пять операций: установка, запуск, статус, логи, остановка.
- **SC-002**: 100% переменных корневого env-примера объяснены в README или связанном справочнике локальных env.
- **SC-003**: Описаны три сценария расширения: Workspace, Project и пакет monorepo.
- **SC-004**: Список корневых команд сокращён; для 100% удалённых aliases указана исполнимая замена.
- **SC-005**: Проверка ссылок и зависимостей не обнаруживает новых неразрешимых команд и локальных ссылок.

- **SC-006**: Все переменные deployment-шаблона объяснены отдельно от local/test defaults и распределены по процессам/этапу сборки.

## Assumptions

- Аудитория — разработчики, впервые запускающие и расширяющие репозиторий.
- Основной локальный сценарий — полный QA pilot с локальными адаптерами; foundation описывается отдельно.
- Устоявшиеся термины и идентификаторы сохраняются; поясняющий текст пишется по-русски.
- Runtime, права доступа, бизнес-правила, зависимости и секреты не меняются.
- Очистка относится к корневому package.json; редкие проверки сохраняются в tools и Nx.

## Уточнение пользователя

Настройки local/test отделены от реального деплоя. Deployment-шаблон предназначен для
корпоративного NON_PROD и не подтверждает завершение host-сборки.
