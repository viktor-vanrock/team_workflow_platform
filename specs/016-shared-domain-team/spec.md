# Feature Specification: Общая предметная команда и навигация

**Feature Branch**: `codex/016-shared-domain-team`
**Created**: 2026-09-09
**Status**: Implemented and validated
**Input**: Сделать хлебные крошки ссылками; удалить роль «Аудитор» и её связи; одна QA-команда из двух исполнителей обслуживает все проекты, роли различаются по предметной области, а не по проекту. Разработка через Spec Kit.

## User Scenarios & Testing

### User Story 1 - Переходы по хлебным крошкам (Priority: P1)

Пользователь открывает главную, выбранный проект и текущий раздел по пунктам в верхней навигации.

**Why this priority**: Отображаемый путь должен помогать перемещаться по приложению.
**Independent Test**: Нажатие каждой ссылки и переход клавиатурой открывают соответствующую страницу.

**Acceptance Scenarios**:

1. **Given** открыта страница проекта, **When** нажата «Архив ордена», **Then** открывается главная.
2. **Given** выбран ALPHA, **When** нажата «Проект ALPHA», **Then** открывается страница ALPHA.
3. **Given** открыт раздел «Проекты», **When** нажато его название в пути, **Then** открывается каталог проектов.

### User Story 2 - Полное удаление роли аудитора (Priority: P1)

В рабочей области больше нет отдельного аудитора, его активных назначений и доступов.

**Why this priority**: Удалить ненужную роль из фактической модели, а не только из списка.
**Independent Test**: Роль отсутствует при входе; старая учётная запись не проходит вход и не имеет действующих прав после обновления существующих данных.

**Acceptance Scenarios**:

1. **Given** свежий или ранее запущенный стенд, **When** загружены роли, **Then** аудитора нет.
2. **Given** ранее существовал аудитор, **When** применено обновление, **Then** его назначения, членство и разрешения удалены, старый вход отвергается.
3. **Given** есть журнал действий, **When** роль удалена, **Then** история решений и событий сохранена для уполномоченного владельца.

### User Story 3 - Одна QA-команда во всех проектах (Priority: P1)

Два QA-исполнителя имеют одну роль «Исполнитель QA» и работают в любом проекте своей рабочей области. Проект выбирается отдельно от учётной записи; для нового проекта не требуется отдельная роль.

**Why this priority**: Штат общей команды не должен размножаться вместе с проектами.
**Independent Test**: Каждый из двух исполнителей переключается ALPHA → BETA без выхода, получает список запросов/очередь и выполняет разрешённые QA-действия в обоих проектах.

**Acceptance Scenarios**:

1. **Given** два исполнителя QA, **When** любой выбирает ALPHA или BETA, **Then** сохраняются его личность и роль, меняется только рабочий проект.
2. **Given** зарегистрирован новый проект этой рабочей области, **When** команда открывает список проектов, **Then** новый проект доступен без отдельного назначения каждому QA.
3. **Given** QA-исполнитель, **When** он пробует административное действие или доступ к другой рабочей области, **Then** доступ отклонён.
4. **Given** проект приостановлен или доступ явно отозван, **When** запрошена работа в нём, **Then** ограничения соблюдаются.
5. **Given** переход между проектами, **When** переключение завершено, **Then** данные и выбранный запрос предыдущего проекта не остаются в новом контексте.

### Edge Cases

- Старый токен аудитора, повторный запуск обновления, существующие ссылки на исторического участника.
- Нет доступных проектов; запрос несуществующего/чужого проекта; отозванное членство.
- Смена проекта во время загрузки; возврат назад и модифицированный клик по ссылке.
- В BETA иной уровень конфиденциальности: команда получает нужный допуск явно, проверки классификации сохраняются.
- Сервисная учётная запись и пользователь другой рабочей области не получают командный доступ автоматически.

## Requirements

### Functional Requirements

- **FR-001**: Все три пункта верхнего пути MUST быть настоящими ссылками на главную, страницу выбранного проекта и соответствующий раздел; текущая страница обозначена для вспомогательных технологий.
- **FR-002**: Система MUST удалить аудитора из ролей, входа, начальных данных, активных назначений и документации текущего поведения.
- **FR-003**: Обновление MUST убирать действующие связи аудитора в существующих данных повторяемо, сохраняя исторические события.
- **FR-004**: Роль человека MUST описывать функцию и предметную область; названия проектов не входят в пользовательские названия ролей.
- **FR-005**: Два отдельных QA-исполнителя MUST иметь одинаковые QA-права во всех существующих и новых проектах своей рабочей области.
- **FR-006**: Пользователь MUST выбирать доступный проект отдельно от входа/смены роли.
- **FR-007**: Командный доступ MUST сохранять проверку членства, явных запретов, срока действия, классификации и разрешённого действия; чужая рабочая область недоступна.
- **FR-008**: Смена проекта MUST очищать проектные данные и выбранные сущности; при ошибке переключения прежний контекст остаётся согласованным.
- **FR-009**: Изменение MUST подтверждаться проверками авторизации, обновления данных и пользовательского сценария двух исполнителей.

### Key Entities

- **Участник**: конкретный человек с устойчивой идентичностью и членством в рабочей области.
- **Предметная роль**: набор разрешений команды, например «Исполнитель QA» или «Руководитель QA», независимо от проекта.
- **Проект**: отдельный рабочий контекст с данными, состоянием и классификацией.
- **Командный доступ**: явное право роли работать со всеми проектами своей рабочей области с соблюдением ограничений.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 3 из 3 пунктов пути открывают ожидаемые страницы мышью и клавиатурой.
- **SC-002**: 0 активных назначений роли аудитора после обновления; 0 вариантов аудитора при входе.
- **SC-003**: 2 из 2 QA-исполнителей работают в ALPHA и BETA с одной ролью; переключение занимает одно действие без повторного входа.
- **SC-004**: Новый проект не требует создания новых ролей или копий исполнителей; все отрицательные проверки чужой области, запретов и недостаточных прав проходят.

## Assumptions

- «Все проекты» означает проекты текущей рабочей области; граница между рабочими областями остаётся обязательной.
- Основной рабочий контур — QA; существующий локальный модуль техписателей (feature 015) сохраняется вместе с документами и отдельной рабочей областью. Механизм не привязывает роль к ключу проекта.
- Два исполнителя — два человека с одинаковой ролью, а не два названия роли по проектам. Имена не заданы, используются «QA 1» и «QA 2».
- Приостановленные проекты остаются видимыми в каталоге уполномоченных ролей, но не становятся рабочими.
- Удаляется роль аудитора и её действующие связи; журнал действий и историческое авторство сохраняются.
- Требования этой спецификации заменяют старое распределение локальных персон по ALPHA/BETA; исторические спецификации сохраняют прежний контекст.

- При интеграции обнаружена готовая feature 015 в другой рабочей копии. Она включена в checkout без изменений пользовательских документов; текущая feature перенумерована в 016.
