# Feature Specification: отдельный Hermes для первого запуска

**Feature Branch**: `main` (новая ветка не запрошена)
**Created**: 2026-09-10
**Status**: Implemented; local verification passed, live provider smoke pending operator configuration
**Input**: «подготовим отдельный сервис с гермесом, он необходим для первого запуска; начинай со спек кит». Уточнение: «Отдельный сервис с LLM и локальным резервным режимом».

## User Scenarios & Testing

### User Story 1 - Запуск Hermes вместе с платформой (Priority: P1)
Оператор получает отдельно запускаемый Hermes и видит его готовность, версию и режим.
**Why this priority**: обязательный компонент первого запуска по запросу пользователя.
**Independent Test**: запустить комплект и перезапустить только Hermes.
**Acceptance Scenarios**:
1. **Given** настроенная установка, **When** запускается комплект, **Then** Hermes запускается отдельным процессом.
2. **Given** ошибочная конфигурация соединения или модели, **When** сервис запускается, **Then** он отказывает с безопасным кодом, без ложной готовности.
3. **Given** сохранённый диалог, **When** Hermes перезапущен, **Then** история и проекты сохраняются.

### User Story 2 - Создание проекта с помощью LLM (Priority: P1)
Заказчик описывает проект свободным текстом, получает уточнение или карточку, исправляет её и подтверждает создание.
**Why this priority**: сервис участвует в пользовательском сценарии первого запуска.
**Independent Test**: диалог через отдельный сервис до проекта, затем три повтора подтверждения.
**Acceptance Scenarios**:
1. **Given** настроенная доступная модель, **When** заказчик описывает проект, **Then** Hermes использует модель для предложения названия и цели.
2. **Given** готовая карточка, **When** человек подтверждает её, **Then** создаётся ровно один свой проект.
3. **Given** текст с командами назначить права или изменить чужие данные, **When** он обработан моделью, **Then** меняются только разрешённые поля предложения.

### User Story 3 - Продолжение при сбое (Priority: P2)
При недоступной модели или Hermes заказчик продолжает локальный сценарий, оператор видит состояние зависимости.
**Why this priority**: модель не должна блокировать первый запуск и ручную работу.
**Independent Test**: вызвать timeout, неверный ответ и остановку Hermes, восстановить сервис и повторить запрос.
**Acceptance Scenarios**:
1. **Given** модель или Hermes недоступны, **When** отправлено сообщение, **Then** ограниченное ожидание завершается локальным ответом.
2. **Given** неизвестный исход предыдущего запроса, **When** повторён тот же запрос, **Then** возвращается сохранённый результат без повторной мутации.
3. **Given** медленный ответ модели, **When** другой человек работает с проектами, **Then** его работа не ждёт завершения обработки модели.

### User Story 4 - Работа Hermes в Mattermost (Priority: P1)
Пользователь вызывает `/hermes ask <вопрос>` или `/hermes test <описание>` в подключённом канале проекта. Hermes использует текущую карточку и опубликованные настройки QA этого проекта. Команда test создаёт QA Intake Draft от проверенного автора; готовность, уточнения и подтверждение остаются явными.
**Why this priority**: пользователь требует запросы на тестирование в нужных проектах, а не только создание проектов.
**Independent Test**: два проекта/автора, настоящая HTTP slash-команда, повтор trigger, отзыв привязки и доступа, недоступная модель.
**Acceptance Scenarios**:
1. **Given** канал с однозначной привязкой к проекту и проверенная identity автора, **When** приходит test, **Then** создаётся ровно один QA-черновик правильного проекта и возвращается личная карточка с недостающими полями.
2. **Given** чужой канал/проект или отозванные права, **When** приходит ask/test, **Then** данные не читаются и черновик не создаётся.
3. **Given** вопрос, **When** Hermes отвечает, **Then** использует только переданный явный контекст, без RAG, поиска, embeddings и памяти других сообщений.
4. **Given** повтор той же команды или изменение прав во время модели, **When** ответ готов, **Then** проверка прав повторяется, дубль черновика не возникает.

### Edge Cases
- Недопустимые поля, длины, версия контракта, чужая идентичность ответа отклоняются.
- Отозванные права и устаревшая версия повторно проверяются после ответа модели.
- Неверная модель, timeout, 429/5xx, неверный JSON и попытки назначения прав включают локальный резерв.
- Секреты и текст диалога не попадают в health-ответы и журналы.

## Requirements

### Functional Requirements
- **FR-001**: Поставка MUST содержать отдельный Hermes и инструкцию запуска, проверки и перезапуска.
- **FR-002**: Hermes MUST поддерживать настраиваемую внешнюю LLM для предложения карточки и локальный резерв без внешних credentials.
- **FR-003**: Платформа MUST владеть историей, текущими правами и подтверждением создания от имени человека.
- **FR-004**: Запрос и ответ MUST иметь фиксированную версию и идентичность; ответ проверяется до сохранения.
- **FR-005**: Неавторизованное обращение и недопустимые входы MUST отклоняться.
- **FR-006**: Сбой модели или Hermes MUST иметь ограниченное ожидание и детерминированный резерв.
- **FR-007**: Повторы MUST сохранять идемпотентность и изоляцию заказчиков; права и версия повторно проверяются после ожидания.
- **FR-008**: Оператор MUST видеть готовность и режим без содержимого диалогов.
- **FR-009**: Модели MUST передаваться только карточка, явный контекст выбранного проекта и текущее сообщение, без полномочий, секретов, чужих данных и общей памяти.
- **FR-010**: Реализация MUST включать автоматические проверки реального соединения, модели, отказов, повторов и прав.

- **FR-011**: Сервис MUST поддерживать вопросы и подготовку QA-запроса из Mattermost с явным проектным контекстом, без RAG по последнему указанию пользователя.
- **FR-012**: Проект MUST определяться опубликованной привязкой канала, автор — verified external identity mapping и текущими правами. User name/email/text не выбирают authority.
- **FR-013**: Новые запросы на тестирование MUST сохраняться как идемпотентные QA Intake Draft; принятый Work Item/Jira issue только через существующее human confirmation.
- **FR-014**: Ответ Mattermost MUST быть ephemeral автору. Произвольные response_url/outbound targets и сообщения в другие каналы не используются.

- **FR-015**: Явное подтверждение в MM MUST связывать автора, канал, точную карточку, Jira project/type, версии bindings и срок; повтор ставит одну durable Jira-команду.

### Key Entities
- **Project dialogue**: приватная история, версия, карточка, состояния COLLECTING / READY / CREATED.
- **Proposal request**: ограниченный шаг диалога, связанный с рабочей областью, заказчиком, диалогом, версией и ключом повтора.
- **Proposal**: ограниченные поля карточки; не созданный проект и не назначение прав.
- **Service status**: версия, настроенный режим и доступность обработки.

## Success Criteria

### Measurable Outcomes
- **SC-001**: Оператор запускает и проверяет Hermes по одной инструкции без изменений кода.
- **SC-002**: Сценарий «описание → уточнение → подтверждение» создаёт один проект при трёх повторах подтверждения.
- **SC-003**: При сбое ответ локального сценария приходит не позднее 5 секунд на контрольном стенде.
- **SC-004**: Все проверки подмены ответа, доступа, повторов и недопустимого ответа модели проходят.
- **SC-005**: Перезапуск Hermes сохраняет все истории и проекты контрольного сценария.

## Assumptions
- Hermes означает существующего координатора платформы; сторонний продукт не назван.
- Первый запуск включает диалог создания проектов и опционально настроенные Mattermost ask/test. Автономные Agent Runs, QA execution и Jira acceptance требуют готовности полного pilot; новые QA-черновики сохраняются до неё.
- Внешний провайдер, модель и секрет задаются оператором. До подключения доступен явный локальный режим.
- Существующие human authority, scope, audit, idempotency и approvals не ослабляются.
